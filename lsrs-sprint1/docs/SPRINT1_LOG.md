# Sprint 1 구현·1차 오류 수정 기록

이 문서는 AI가 이번 작업에서 실제 수행한 구현과 검증을 정리한 기록입니다. 팀원의 작업 시간, 회의, 승인, 사용자 검수 결과를 대신 기록하지 않았습니다.

## 수행한 작업

| 단계 | 실제 수행 내용 | 산출물 |
|---|---|---|
| 자료 복습 | 최신 시스템 구조 설계·개발 환경, 최종 Backlog, 문제정의서 재확인 | Sprint 1 8개/41 SP 확정, AC 추적표 |
| 개발 환경 | Java 21, Gradle Wrapper, Spring Boot, JPA/H2, Flyway, Security/JWT 구성 | 빌드 설정·프로필·DB 스키마 |
| 가입·권한 | BCrypt, 이메일 토큰 해시/만료/단일 사용, SMTP/파일 메일, JWT·역할 검증 | 가입·로그인·인증 화면/API |
| 조회·예약 | 좌석 48개, 시간 검증, 현재 정책 안내, 예약/정책 버전 검증 | 학생 그리드·예약 확인창 |
| 동시성 | User→Seat→Reservation 잠금, 잠금 후 겹침 재검사 | 서비스·동시 경합 테스트 |
| 체크인·퇴실 | 브라우저 QR 판독, 소유권·좌석·시각·상태 검증, 조기 반환 | 카메라/이미지 입력·관리자 QR |
| 화면 검증 | 가입→메일 인증→예약→체크인→퇴실, 오류·모바일·카메라 입력 | Playwright 검증 스크립트·JSON 결과 |
| 실행 파일 검증 | 실제 SMTP 프로토콜, 파일 DB 재시작, 키/QR 유지, HTTP 조회 | Python 런타임 검증·JSON 결과 |
| 전달 준비 | 깨끗한 빌드, 보고서, 실행 스크립트, 사전 빌드 JAR | ZIP 배포본 |

## 발견한 문제와 조치

| 문제 | 확인된 원인 | 수정/해결 | 재검증 |
|---|---|---|---|
| 초기 의존성 다운로드 실패 | 실행 환경의 프록시·인증서 설정 불일치 | 검증용 환경의 신뢰 저장소·현재 프록시 적용, 프로젝트에는 환경 전용 값을 넣지 않음 | 컴파일·전체 빌드 성공 |
| 초기 테스트 컴파일 오류 | 응답 문자열 helper `content()`와 MockMvc matcher 이름 충돌 | contentType matcher 호출을 명시적으로 구분 | 테스트 컴파일·실행 성공 |
| 선택 좌석이 있어도 예약 버튼 비활성화 유지 | 조회 완료 전 `loading` 상태에서만 요약을 렌더링 | finally에서 loading 해제 후 요약 상태 갱신 | 브라우저 새로고침 후 선택·예약 가능 확인 |
| 초기 시연 데이터의 같은 학생 겹침 | 사용 중/예약됨 두 예시를 같은 계정에 배정 | 서로 다른 학생 계정으로 seed 분리 | 첫 화면 두 상태·실제 예약 흐름 확인 |
| JWT 정확한 만료 경계 모호함 | 기본 timestamp 검증만으로 정확한 경계·exp 필수 조건이 충분히 드러나지 않음 | exp 존재와 `now < exp`를 명시 검증 | 정확히 60분 만료·exp 없는 서명 토큰 거부 |
| 미지원 JSON 필드가 무시될 수 있음 | 기본 역직렬화 설정 | unknown properties 거부 설정 | 역할 위조 필드 포함 요청 400 |
| 메일 본문의 유효시간 고정 문자열 | 설정 변경 시 본문과 실제 만료 불일치 가능 | 같은 verification-minutes 설정으로 본문 생성 | 빌드·SMTP 인증 흐름 성공 |
| 브라우저 검증 도구 시작 실패 | 일반 Chromium의 프로세스 소켓 제한 및 다운로드 경로 문제 | 검증 환경에서 호환되는 headless shell과 ICU 리소스 사용 | 실제 브라우저 13개 항목 실행 |
| 자동 시연 로그인 초기 401 | HTTP 포트가 열리는 시점과 demo 초기 데이터 커밋 시점 차이 | 테스트가 demo 초기화 완료까지 재시도하도록 수정 | 새 임시 DB로 전체 흐름 재실행 |
| 전체 예약 테스트의 단언 실패 | 빈 필터 결과에 JsonPath `.length()`를 적용한 테스트 표현 문제 | 필터 결과에 `isEmpty()` 사용 | 48석 실제 예약 DB 테스트 통과 |

의도한 정책 오류(잘못된 QR, 중복 예약, 타인 접근 등)는 애플리케이션 결함으로 간주하지 않고 실패해야 하는 입력으로 검증했습니다. 전체 검증의 실제 횟수·결과·한계는 `TEST_REPORT.md`와 원시 보고서에서 확인할 수 있습니다.

## 이어서 개발할 때

Sprint 2의 노쇼·만료 Job은 이 프로젝트의 `Clock`, 정책 버전, 활성 예약 상태, 고정 잠금 순서를 재사용해야 합니다. 특히 체크인과 자동 취소가 동시에 들어오는 경우 한 번만 상태 전이·노쇼 누적이 일어나도록 별도 테스트가 필요합니다. 기존 예약의 입실 기한은 다시 계산하지 않습니다.

Git 원격 저장소는 제공되지 않아 커밋·푸시·PR·배포를 수행하지 않았습니다. 이번 결과는 로컬에서 실행 가능한 프로젝트이며 사용자의 최종 만족도 검수는 아직 진행되지 않았습니다.
